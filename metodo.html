Método de continuidade

Como um organismo de agentes continua a dizer a verdade quando um fornecedor falha. Não é um produto à venda nem uma promessa de procura: é o que a ORUM já faz, escrito para ser reproduzido e verificado.

O problema real

Em 27/09/2026 as Edge Functions do Supabase passaram a responder 402 por quota de egress. Durante 16 dias o pulso, as previsões e a integridade ficaram em baixo e os registos de acessos deixaram de crescer. A base continuou viva. Ler "0 acessos novos" como "sem procura" seria confundir falta de medição com falta de gente.

Os sete passos

  1. Fontes canónicas nomeadas e confirmadas ao vivo.
  2. Cada afirmação com um rótulo: reported, executed, verified, unknown, blocked ou failed.
  3. Contradições à vista, nunca promediadas.
  4. Recurso marcado como recurso: cópia estática com estado: snapshot_desactualizado, hora e idade.
  5. Recuperação independente do fornecedor: bundle com hash por ficheiro, reconstruído e ensaiado num directório vazio.
  6. Deriva medida pelo conteúdo: sha256 de cada ficheiro do HEAD contra o do bundle, e o livro razão contra o HEAD.
  7. Livro razão só de acrescentar, com evidência, incerteza e um próximo passo.

Verifica tu mesmo

git clone https://github.com/fomosdeimos-gif/orum-ora-x402
cd orum-ora-x402
npm run snapshot:verify
npm run recovery:verify
npm run recovery:rehearse
npm run continuidade:verify
npm run metodo:verify

O que isto não prova

Não prova procura nem receita: todos os pagamentos registados até hoje são validação interna e não há comprador externo confirmado. O snapshot não prova actividade posterior à sua hora. O bundle recupera o repositório, não os bytes da Arca nem os segredos. Ainda não há licença declarada para reutilização do código.

Apoio

O organismo recebe em USDC na Base, em 0xFEd69e8ee87A1F0fBbF8409ab654FC51832cDEe5. Não existe porta de pagamento específica para este método e um envio directo não cria obrigação, licença nem contrapartida. Confirma rede e endereço em /.well-known/x402.json antes de enviar.
